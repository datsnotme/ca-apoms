# DATABASE_DESIGN.md

## Conventions

- Table names: `snake_case`, plural.
- Primary keys: `id` (unsigned bigint, auto-increment).
- Foreign keys: `{singular_table}_id`, indexed, `constrained()->restrictOnDelete()` unless a
  cascade is explicitly correct (e.g., a pivot row belonging entirely to its parent).
- Timestamps: `created_at`, `updated_at` on every table. `deleted_at` (soft delete) on any
  table representing an institutional record that may already be referenced elsewhere
  (students, faculty, departments, programs, curricula, courses, grades, documents,
  equipment, etc.) per business rule "archived records must not appear in active lists by
  default" and "deleting referenced academic records should be prevented."
- Status/category fields use PHP backed enums (`App\Enums\...`) validated at the application
  layer and stored as `string` columns (not MySQL `ENUM`) so new statuses can be added via
  code + migration without an `ALTER TABLE ... MODIFY` schema change.
- Every table frequently filtered or joined on has an index on the relevant foreign key
  and, where applicable, a composite index matching real query patterns (e.g.
  `student_id + academic_year_id + semester_id`).
- Money/points/units: `decimal` columns, never `float`.

### Phase 2 scoping notes (see `ASSUMPTIONS.md` for the full reasoning)

- **No standalone `majors` table.** `programs.major` (shipped in Phase 1) already captures
  "BS Agriculture major in Crop Science" vs. "...major in Animal Science" as a field on the
  program, since in this institution a major is a named variant of one degree program, not an
  independently manageable catalog object.
- **`class_schedules.room` is free text in Phase 2**, not a `facilities` FK — the Facilities
  module doesn't exist until Phase 7. It becomes a real FK once that module ships, via a
  migration that backfills matched facility rows. **Fulfilled in Phase 7C** — see that section
  below.
- **`faculty_assignments` is a table, not a column on `class_sections`**, even though Phase 2
  only ever creates one row per section — Phase 5's workload aggregation reads from this
  table, so the shape is right from the start rather than needing a data migration later.
- **Grading scale is fully configurable** (`grading_scales` / `grading_scale_values`), per the
  explicit spec instruction not to hard-code one grading policy. `student_grades.grade` stores
  the scale value as a string; validity is checked against the *active* scale's values at the
  application layer, not a database constraint (so switching the active scale doesn't require
  a migration).

## Phase 3A: Progress Computation Engine

```mermaid
erDiagram
    STUDENTS ||--o{ ACADEMIC_DEFICIENCIES : has
    CURRICULUM_COURSES ||--o{ ACADEMIC_DEFICIENCIES : "flags"

    ACADEMIC_DEFICIENCIES {
        bigint id PK
        bigint student_id FK
        bigint curriculum_course_id FK
        string deficiency_type "failed|incomplete|not_taken|dropped"
        timestamp detected_at
        timestamp resolved_at "nullable"
        string resolved_via "nullable: retake|substitution|waiver"
        text resolution_notes "nullable"
        timestamp deleted_at
    }
```

### Phase 3A scoping notes (see `ASSUMPTIONS.md` for the full reasoning)

- **Checklist status and GWA are computed on demand, not cached** — `ProgressComputationService`
  walks the student's curriculum courses against their `enrollment_courses`/`student_grades`
  every time the Progress page loads. `academic_deficiencies` is the one piece that *is*
  persisted, because a deficiency needs a resolution workflow (retake/substitution/waiver, with
  notes) to attach to — a plain computed value has nothing to attach a resolution to.
- **"GWA" (General Weighted Average), not "GPA"** — the seeded grading scale is the Philippine
  1.00 (highest) – 5.00 (lowest) convention already established in Phase 2A, so a lower average
  is better. Calling it "GPA" would misrepresent the scale's direction to anyone used to a
  higher-is-better system.
- **A deficiency only exists for a course whose expected year level has already passed** —
  `curriculum_courses.year_level < student.year_level (current)`. A required course still ahead
  of the student on their curriculum is "pending," not a deficiency, even if `not_taken`.
- **The best attempt wins, not the latest.** If a student failed a course once and passed it on
  a later retake, the checklist shows `completed` — the failed attempt still exists in
  `student_grades`/`grade_change_logs` for audit purposes, it just doesn't drive the checklist
  status once superseded.

### Phase 3B scoping notes (see `ASSUMPTIONS.md` for the full reasoning)

- **`students.adviser_id` (built in Phase 2C) remains the single editable field for adviser
  assignment.** `student_advisers` is a read-only history log, auto-written by a `Student` model
  event exactly like `student_status_histories` already does for status changes — there is no
  separate "assign adviser" form. Reassigning closes the previously-active row
  (`unassigned_at = now()`) and opens a new one; only one row per student may have
  `unassigned_at IS NULL` at a time, enforced at the application layer.
- **`advising.manage` excludes the Dean role.** The spec explicitly scopes "record
  advising/intervention" to Admin/Department Head/Faculty only — Dean gets `advising.view` for
  college-wide oversight but never creates or edits a session record.

## Phase 3C: At-Risk Monitoring

```mermaid
erDiagram
    STUDENTS ||--o{ PROGRESS_ALERTS : triggers

    PROGRESS_ALERTS {
        bigint id PK
        bigint student_id FK
        string alert_type "multiple_deficiencies|low_gwa|enrollment_status"
        string severity "warning|critical"
        text message
        timestamp triggered_at
        bigint acknowledged_by FK "nullable, users.id"
        timestamp acknowledged_at "nullable"
        timestamp resolved_at "nullable"
    }
```

### Phase 3C scoping notes (see `ASSUMPTIONS.md` for the full reasoning)

- **Three fixed rules, each independently evaluated and independently resolved**, unique per
  `(student_id, alert_type)`: 2+ unresolved deficiencies (4+ escalates to critical); GWA at or
  above 3.00 — the last passing value on the seeded scale — with 4.00+ (failing range)
  escalating to critical; and a student status of `on_leave`/`inactive` (warning) or `withdrawn`
  (critical). `ProgressAlertService::evaluate()` is the single place these thresholds live.
- **Re-syncing is scoped, not global.** The at-risk list (`/academic-progress`) re-evaluates
  every student *within the viewer's own visibility scope* (a Faculty member's advisees, a
  Department Head's department, or the whole college for Admin/Dean) on each visit, rather than
  running against every student in the database or on a schedule — see `ASSUMPTIONS.md` for the
  scale tradeoff this implies.
- **An alert that re-triggers after being resolved needs to be acknowledged again.** Resolving
  an alert does not delete it (so its history survives), and `syncAlerts()` clears
  `acknowledged_by`/`acknowledged_at` specifically when re-opening a previously-resolved row —
  otherwise a brand-new occurrence of the same alert type would silently inherit "already
  reviewed" status from whatever caused the *last* occurrence.

  Phase 4 in `PROJECT_PLAN.md`'s technology table, so introducing PDF generation here would jump
  ahead of the plan for a capability nothing in Phase 3 actually requires.

### Phase 4A scoping notes (see `ASSUMPTIONS.md` for the full reasoning)

- **`gwa_snapshot`, `completion_percentage_snapshot`, and `deficiency_count_snapshot` are
  deliberately frozen at nomination time — the one exception to this project's "compute on
  demand, never persist" rule** established in Phase 3A. A graduation record must not silently
  drift if a grade is edited months after nomination; the live, current values are always
  reachable via the existing Progress page (`View Progress` link on the candidate show page),
  so nothing is lost by freezing the graduation-record copy.
- **No `graduation_evaluations` table.** `GraduationCandidate.status` is the single umbrella
  status field carrying a candidate from `nominated` through `graduated` — the same
  no-redundant-status-table approach used for `student_progress_snapshots` in Phase 3A. Phase
  4B–4D advance this same `status` column rather than introducing a parallel evaluation-state
  table.
- **`graduation.view`/`graduation.manage` cover both requirement templates and candidates.**
  Dean and Department Head get `.view` only in 4A (their recommend/approve involvement starts
  in Phase 4C); only Administrator gets `.manage`, and `GraduationCandidatePolicy`/
  `GraduationRequirementTemplatePolicy` additionally hard-require the Administrator role on
  every mutating action — Phase 4 spec treats "preparation" (nominate, edit checklist) as
  Admin-only, distinct from "recommend" (Dept Head) and "approve" (Dean) in later sub-phases.
- **Eligibility is computed, not stored.** `GraduationCandidateService::identifyEligibleStudents()`
  filters active students to those with `ProgressComputationService::completionPercentage() ===
  100.0` and zero unresolved `academic_deficiencies` — reusing Phase 3A's engine rather than
  duplicating checklist logic.
- **`student_graduation_requirements` uses custom short FK constraint names**
  (`grad_requirements_candidate_fk`, `grad_requirements_template_fk`), proactively applying the
  64-character MySQL identifier limit lesson learned in Phase 3D.

- **Assigning a candidate's first evaluator transitions `GraduationCandidate.status` from

  pattern used for adviser reassignment in Phase 3B, rather than a separate manual
  "start evaluation" step.
- **Evaluators must be Faculty from the same department as the candidate's student**, enforced
  in `CompetencyEvaluatorRequest`, not just the UI dropdown — a candidate cannot be assigned an
  evaluator from a different department or a non-Faculty role.
- **`GraduationCandidate::evaluationComplete()` is computed, not stored** — true only when at
  least one evaluator is assigned and every assigned evaluator has a `competency_ratings` row
  for every currently-defined `competency_indicators` row. Mirrors `requirementsComplete()`
  from Phase 4A.
- **`graduation.view`/`graduation.manage` are extended to cover the competency framework too**
  (categories, indicators), and a new `graduation.evaluate` permission is introduced,
  granted to Faculty only — the capability to submit ratings for a candidate they are assigned
  to, checked in `CompetencyRatingRequest` against the specific `competency_evaluators` row,

- **`GraduationCandidate::scopeVisibleTo()` and `GraduationCandidatePolicy::view()` are extended
  for Faculty**: rather than a separate "My Evaluations" page, Faculty now sees the same
  `/graduation-candidates` index and show page as every other role, scoped to only the
  candidates where they hold a `competency_evaluators` row — reusing the existing candidate
  list/detail UI instead of building a parallel one.

### Phase 5C scoping notes (see `ASSUMPTIONS.md` for the full reasoning)

- **`faculty_documents` keys on `user_id` directly**, same as the four Phase 5B tables — the
  document belongs to the faculty member, not to the `faculty_profiles` row.
- **Three separate user references, three separate purposes**: `user_id` (whose document this
  is), `uploaded_by` (who submitted it — may be the faculty member themselves or an Admin),
  `verified_by` (which Admin reviewed it). All three can be different users at once (an Admin
  uploads on a faculty member's behalf, a different Admin later verifies it).
  `uploaded_by`/`verified_by` are `nullOnDelete()` so a deleted user account doesn't cascade
  away the historical document record.
- **`verification_status` reuses the `DocumentVerificationStatus` enum introduced in Phase 2D**
  for `student_documents` — same three-state shape (`pending`/`verified`/`rejected`), same
  reviewer/remarks pattern, no need for a parallel enum.
- **Unlike `student_documents`, there is no `visibility_level` column.** Student documents
  needed a visibility flag because of a (future) student self-service portal concept; faculty
  already authenticate directly into CA-APOMS with role-scoped visibility handled entirely by
  `scopeVisibleTo()`, so a separate per-document visibility flag would be a redundant axis of
  control with nothing to gate.
- **`FacultyDocument::scopeVisibleTo()` uses the same three-tier shape as `FacultyProfile`**
  (Admin/Dean unrestricted, Department Head own department via `user.department_id`, else
  self only).
- **Soft deletes** (`deleted_at`) are used here — unlike the Phase 5B tables — because a
  document's underlying file is physically removed from storage on delete
  (`FacultyDocumentController::destroy()`), and keeping the DB row as a tombstone preserves the
  audit trail (who deleted what, when) without the file itself lingering on disk.

## Phase 5D: Faculty Workload

No new tables. Teaching load is computed on demand from `faculty_assignments` (Phase 2E) joined
through `class_sections` → `courses` (for `units`) and `class_schedules` (for meeting times) —

### Phase 5D scoping notes (see `ASSUMPTIONS.md` for the full reasoning)

- **Every assigned section counts its full course unit value toward the assignee's total**,

  be linked from a Phase 6F notification once that sub-phase exists; a tombstone avoids a
  dangling reference later.
- **`events.start_at`/`end_at` are stored and edited in the application's configured timezone
  (UTC) as plain wall-clock values** — the Edit form round-trips the exact value a user typed,
  with no drift. The read-only Index list, however, renders the stored UTC instant through the
  browser's `Date.prototype.toLocaleString()`, which converts to the *viewer's local timezone*
  for display. In a single-campus deployment where every viewer's OS clock is already set to the
  campus's own timezone, this coincides with wall-clock campus time; it was called out explicitly
  here rather than left implicit so it isn't mistaken for a bug later.

- **Version history is a genuinely new pattern**: a `Document` row is metadata only; each
  `document_versions` row is one uploaded file. `Document::latestVersion()` uses Eloquent's
  `latestOfMany('version_number')` rather than a `current_version_id` pointer column on
  `documents` — one less piece of state to keep in sync, since "the latest version" is always
  derivable from `version_number` alone.
- **`document_versions` has no soft delete**; `documents` does. A version is either kept or
  genuinely removed (with its file), but the parent document (and its full version history)
  should tombstone on delete the same way `FacultyDocument` does, for the same audit reason.
- **A document must always have at least one version.** Deleting the last remaining version is
  blocked at the controller level with a friendly redirect-back error, not a DB constraint — the
  correct action once nothing is left worth keeping is deleting the whole document.

  child data" reasoning that gave `Meeting`/`ResearchProject`/`ExtensionProject` their own Show

### Phase 7D scoping notes (see `ASSUMPTIONS.md` for the full reasoning)

- **No new permission** — `Equipment` reuses `operations.manage`/`operations.view`, the same
  free-design-judgment precedent as `Facility` (Phase 7C): the spec has no equipment-specific
  permission row either.
- **`equipment.department_id` and `equipment.facility_id` are two independent, both-nullable
  fields, not one derived from the other.** `department_id` is organizational ownership (the
  `Facility`/Announcement/Event/Meeting shared-vs-department shape); `facility_id` is current
  physical location. A department's equipment doesn't stop being that department's just because
  it's temporarily housed in a shared facility, so the two must vary independently.
- **`equipment.status` is a persisted enum (`EquipmentStatus`: available/borrowed/
  under_maintenance/retired), not computed on demand** — unlike `FacultyWorkloadService`
  (Phase 5D) or progress computation (Phase 3A), which deliberately avoid a persisted status
  column for genuinely expensive aggregate calculations. Equipment status is a simple state
  machine driven directly by workflow actions (borrow/return/maintenance-start/
  maintenance-complete), the same shape as `Task`/`MeetingActionItem` status — a persisted column
  updated by its own controllers, not a derived aggregate.
- **`equipment_borrowings` and `equipment_returns` are two separate tables, not one table with a
  nullable `returned_at`** — this matches the spec's own literal table names
  (`DATABASE_DESIGN.md`'s planned-schema list names both explicitly), and reads more naturally as
  an audit trail: a borrowing record is written once at borrow time and never mutated; a return
  record is a separate event written once at return time. `equipment_returns.equipment_borrowing_id`
  is unique, enforcing at most one return per borrowing.
- **`equipment_maintenance` stays one table** (unlike borrowings/returns) with a nullable
  `completed_at` meaning "still ongoing" — the spec's planned-schema list names it as a single
  table, and a maintenance record naturally has one lifecycle (reported → in progress →
  completed) rather than two independent events.
- **No `delete()`/`destroy()` for borrowings, returns, or maintenance records** — once recorded,
  they're an immutable accountability trail, not resources to be edited or removed later. Only
  `Equipment` itself supports the usual full CRUD (including soft delete).
- **No persisted `accountabilities` table, despite being named in the original planned-schema
  list.** "Who is accountable for what equipment right now" is entirely derivable as
  `EquipmentBorrowing::whereDoesntHave('return')` — a live query, not a fact that needs its own
  storage. Persisting a parallel `accountabilities` table would create a second source of truth
  that has to be kept in sync with `equipment_borrowings`/`equipment_returns` on every
  borrow/return, for no benefit over querying directly. This is the same
  "computed-on-demand, persisted only where a workflow needs it" philosophy already applied to
  `FacultyWorkloadService` (Phase 5D — no `faculty_workloads` table) and progress computation
  (Phase 3A). The `Equipment/Accountability.tsx` report page and
  `EquipmentAccountabilityController` provide the same information live.
- **`equipment.serial_number` is nullable and unique** — not every item has (or needs) a serial
  number (e.g. simple tools), but when present it must be unambiguous.
- **`equipment_maintenance.performed_by` is a free string, not a `users` FK** — maintenance is
  frequently done by an external vendor or a non-system staff member, not necessarily anyone with
  a login. This is the same "the real-world actor isn't always a system user" reasoning that
  keeps `class_schedules.day_of_week` etc. plain rather than over-normalized.

## Phase 8C: Backup and Restore

**No new tables.** Backups are plain `.sql` files under `storage/app/private/backups/` — the
filesystem is the source of truth for what backups exist; `BackupService::list()` reads the
directory directly rather than tracking rows in a database table (the same "compute on demand"
discipline as every other Phase 8 sub-phase). Who triggered a backup or restore, and when, is
recorded via the existing `spatie/laravel-activitylog` infrastructure under `log_name = "backups"`
— visible in the Phase 1 Audit Logs viewer — rather than a dedicated `backups` table.

- **`mysqldump`/`mysql` are shelled out to via Laravel's `Process` facade**, not a package —
  `barryvdh/laravel-dompdf` and `maatwebsite/excel` cover PDF/Excel (Phase 8B); backup/restore has
  no comparable package need since it's a single database engine (MySQL/MariaDB), not a
  multi-format export.
- **A real, environment-specific bug was found and fixed during live verification**: Symfony
  Process's default environment derivation only fully inherits the parent process's environment on
  the `cli`/`phpdbg`/`embed` PHP SAPIs. `php artisan serve` runs under `cli-server`, which instead
  intersects `getenv()` with `$_SERVER` — and on this Windows host that silently dropped a variable
  `mysqldump.exe`'s own Winsock initialization depends on, failing with `Can't create TCP/IP socket
  (10106)`. `BackupService::mysqlEnv()` now explicitly passes the full `getenv()` to every
  `Process` call, sidestepping the SAPI-dependent filtering entirely. See `ASSUMPTIONS.md` for the
  full diagnostic trail.
- **Filenames are a single closed pattern** (`ca-apoms_YYYY-MM-DD_HHmmss.sql`), enforced both in
  the route (`Route::where()`) and again inside `BackupService` itself — a filename is never taken
  as free-form user input anywhere in the download/restore path, closing off path traversal by
  construction rather than by sanitization.

## Foreign Key and Delete Behavior

- `restrictOnDelete()` is the default for any FK into a table that is itself
  soft-deletable and institutionally significant (departments, programs, students, faculty,
  curricula, courses) — the business rule "deleting referenced academic records should be
  prevented" is enforced at the database level, not just the application level.
- Pivot/detail rows that only make sense attached to their parent (e.g.
  `enrollment_courses` under `student_enrollments`, `competency_ratings` under
  `graduation_evaluations`) use `cascadeOnDelete()`.
- `department_head_id` on `departments` is nullable and does **not** cascade-delete the
  department if the user record is removed — it is set null instead, since a department
  outlives any individual head assignment.
